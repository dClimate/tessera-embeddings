# 005 — Multi-lock-file strategy

**Status:** Accepted (v0.1.0)

## Context

`tessera_embeddings` has to satisfy three different deployment
profiles:

* **Laptop / CI** — CPU torch, any platform, fast install.
* **Production GPU AMI** — Linux x86_64, CUDA 12.1, exact wheel
  match to the trained model's environment.
* **Dev environment** — superset of the laptop case + pytest +
  ruff + mypy + hypothesis.

A single universal lock can't cover all three. CUDA torch wheels
exist only for Linux x86_64; forcing them universal would either
fail to resolve on macOS arm64 (laptop) or silently install the CPU
wheel everywhere (halving production throughput).

## Decision

Ship four lock files, each generated by `lock/lock.sh`:

| File | Platforms | Torch | Purpose |
|---|---|---|---|
| `uv.lock` | universal | CPU | What `uv sync` reads (alias of CPU). |
| `lock/inference-cpu.lock` | Linux x86_64, macOS arm64/x86_64, Linux arm64 | CPU | Laptop dev, CI, plain runner. |
| `lock/inference-cu121.lock` | Linux x86_64 only | CUDA 12.1 | Production GPU. |
| `lock/dev.lock` | universal | CPU | CPU + dev tools. |

CI's `lock-check.yml` workflow regenerates all four when
`pyproject.toml` changes and asserts no diff.

## Rejected alternatives

**Single universal lock with `[gpu]` extra:** uv (and pip)
extras can't conditionally swap a transitively-installed wheel for
a CUDA variant; they can only add new packages. The CUDA torch
wheel comes from a different index URL — not expressible in a
single lock.

**Conda environments:** mainstream OSS users want pip-installable
packages. Conda would solve the CUDA-wheel problem at the cost of
shutting out everyone outside the conda ecosystem. Tessera-trained
models also include `torchvision`, `numcodecs`, and other deps that
have inconsistent conda packaging.

**Generate locks at install time:** `uv sync` against `pyproject.toml`
without locks resolves correctly but is non-deterministic — the
dependency tree changes as upstream releases. We need byte-exact
reproducibility for production GPU runs against the trained model.

## Consequences

- **Pro:** every deployment profile gets the right wheels with no
  install-time guesswork.
- **Pro:** a contributor on macOS can `uv sync` and get a working
  laptop env without thinking about lock files.
- **Pro:** CI catches `pyproject.toml` drift via the
  `lock-check.yml` workflow.
- **Con:** four files to keep in sync. `lock/lock.sh` does this
  in one shot — but if someone runs `uv lock` manually instead,
  they'll generate `uv.lock` only and the others will drift.
  Mitigated by the CI check.
- **Con:** the CU121 lock pins CUDA 12.1 specifically. CUDA
  upgrades require a coordinated rebuild of the production AMI +
  lock file.
